## Proposed architecture

Use a static, immutable build on a HostLimo root-app trust edge. Knot (or the established authoritative service) owns DNS/DNSSEC; nginx serves both native HTTP and DANE HTTPS. `welcome.host.limo` serves the same artifact to ordinary browsers. Akash is unnecessary for the MVP.

## Onboarding sequence

1. Confirm the controlling wallet output and completed auction/registration state from a current HSD/Bob source.
2. Allocate the intended HostLimo server and verify its SSH host key through a trusted channel.
3. Inventory the live node layout, service units, ports, backups, and existing manifests. Do not use the historical Handout key generator.
4. Generate fresh `welcome`-only KSK, ZSK, and TLS private key on the approved host. Never copy material from `iamthat`, `xn--e88h`, or another name.
5. Independently calculate the DS key tag/digest and TLSA `3 1 1` SPKI digest. Record only public values in the change plan.
6. Stage the signed zone and nginx HTTP/HTTPS configuration. HTTP serves the app directly; it does not force HTTPS. HTTPS uses the fresh key/certificate. Both routes expose `/healthz` or an equivalent static health response.
7. Build and checksum an immutable application release. Stage it in a versioned directory, keep the previous artifact, validate content locally, and run `nginx -t` without reloading.
8. Back up and hash the pre-change authoritative config, zone, service definitions, nginx config, certificate/key, DNSSEC material, manifest, and current HNS parent resource. Keep private backups off-repository.
9. Present exact before/after parent records, signed zone public records, DS calculation, TLSA calculation, server IP, backup paths/hashes, and rollback commands for owner approval.
10. After explicit approval, publish the signed authoritative zone and validate it directly before any parent update. Reload only after config validation.
11. Submit the approved parent NS/GLUE/DS transaction. Record transaction ID, confirmation and activation heights. Do not remove an old trust anchor in the same change that introduces a replacement.
12. Verify after activation: authoritative RRSIGs; parent DS to KSK; recursive `AD=true`; A/NS/DNSKEY/TLSA; live SPKI-to-TLSA match; HTTP 200; HTTPS 200; SkyInclude/DANE browser success; `welcome.host.limo`; monitoring; and immutable rollback.

## nginx intent

Two explicit server blocks share the versioned static root: port 80 serves native HTTP; port 443 serves HTTPS with the `welcome` certificate/key and modern TLS settings. The normal-browser companion is a separate `welcome.host.limo` WebPKI server block that serves the same release. Validate configuration and backup before any approved reload.

## Rollback

Application failure: repoint the release symlink to the previous checksum-verified artifact, validate nginx, reload after approval, and leave DNS untouched.

TLS application failure before parent activation: restore the backed-up zone/nginx/certificate state; do not publish parent records.

Trust-chain failure after activation: keep HTTP online, restore the last working signed zone and TLS key/certificate, retain additive DS/TLSA overlap when used, and revert parent records only through a separately reviewed on-chain change.
